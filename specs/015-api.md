# The API

## Overview

`toposd`'s public API: agents and their versions, sessions, their
events (listed, sent and streamed from a sequence number), fork,
rewind, redaction and scope, triggers, credentials, and memory stores
with their document versions. Every route is under `/v1`, which
[[030-shared-origin]] lets an installation replace with a base path.
Every request is verified and asked of the authorizer
([[006-identity]]); every error is one `latere.ai/x/pkg/httpjson`
envelope with a code from one table; lists page with `cursor` and
`next_cursor`; every `POST` takes an `Idempotency-Key`. The committed
`api/openapi.yaml` and the handlers agree, by test.

## Current state

v0.7.0 had no API. The retired hosted service ran a synchronous
autonomous run behind an ingress's 60 second read timeout, and its live
attach had to reach the one replica that owned the session. Borrowed
from it: attach as replay then live tail, which here is a Server-Sent
Events stream any replica can serve because the log is in the store.
Nothing else is carried.

## Design

### Routes

Collection paths are relative to the API root, `/v1` by default. JSON
bodies are snake_case except manifests, which are the camelCase objects
of [[003-manifest]], accepted as YAML or JSON and answered as JSON.

| Method and path | Action ([[006-identity]]) | Does |
|---|---|---|
| `PUT /v1/agents/{name}` | `agent.create` or `agent.update` | apply an Agent manifest to the caller's own agent of the name (below); answers the resolved manifest with `status`; a changed digest creates a version, and a change to the metadata alone (`metadata.displayName`, labels, annotations) replaces the latest version's metadata and creates none ([[003-manifest]]) |
| `GET /v1/agents`, `GET /v1/agents/{ref}` | `agent.list`, `agent.read` | list; get by `agent_` id, or by name among the caller's own agents |
| `GET /v1/agents/{ref}/versions`, `GET /v1/agents/{ref}/versions/{n}` | `agent.read` | the versions and one version's resolved spec |
| `POST /v1/agents/{ref}/archive` | `agent.archive` | archive; running sessions keep their version. The body `{"permanent": true}` is required, because archiving cannot be undone: the agent's identity is disabled after its last session and never returns, and applying it again creates a new agent; a client shows that before it sends the request. Without it the answer is `confirmation_required` and nothing changes |
| `POST /v1/sessions` | `session.create` | create a session (the body below); answers 201 with the Session |
| `GET /v1/sessions`, `GET /v1/sessions/{id}` | `session.list`, `session.read` | list, filtered by `agent`, `status`, `runner` and `archived` (below); get, archived or not |
| `GET /v1/sessions/summary` | `session.list` | how many sessions the list would answer under the same filters, by status, and how many agents they belong to (below) |
| `PATCH /v1/sessions/{id}` | `session.read`, then `session.update` | change the model the session's next turn runs, its reasoning effort, or both (below); appends `session.model_changed` |
| `POST /v1/sessions/{id}/end` | `session.end` | end `completed` or `canceled` (body `reason`) |
| `DELETE /v1/sessions/{id}` | `session.delete` | delete the session, its log and its blobs ([[014-store]]) |
| `GET /v1/sessions/{id}/events` | `session.read` | list events from `from_seq`, paged |
| `POST /v1/sessions/{id}/events` | `session.send`, or `session.interrupt` for `user.interrupt` | send one user event (below) |
| `GET /v1/sessions/{id}/stream` | `session.read` | the Server-Sent Events stream (below) |
| `GET /v1/sessions/{id}/blobs/{digest}` | `session.read` | a blob's bytes |
| `POST /v1/sessions/{id}/fork` | `session.read`, then `session.fork` | fork at a turn boundary, body `{"at_seq": N}` with `at_seq` optional, the last turn boundary when absent; answers 201 with the new Session; any session the caller may read, an ended or expired one included; semantics [[017-external-runners-handoff-fork]] |
| `POST /v1/sessions/{id}/archive`, `POST /v1/sessions/{id}/unarchive` | `session.read`, then `session.update` with `archived` | set or clear the session's `archived_at` (below); answers the Session |
| `POST /v1/sessions/{id}/rewind` | `session.rewind` | restore a turn's checkpoint; semantics [[034-checkpoints-and-rewind]] |
| `POST /v1/sessions/{id}/events/{event_id}/redact` | `session.redact` | tombstone one event; semantics [[004-session-log]], [[018-credentials-and-secrets]] |
| `POST /v1/sessions/{id}/resume` | `session.resume` | resume a session idle with `budget`, optionally with a new budget; appends `session.resumed`; any other status is `conflict` ([[007-models]]) |
| `PATCH /v1/sessions/{id}/scope` | `session.scope` | narrow or widen the session scope; appends `session.scope_changed` ([[018-credentials-and-secrets]]) |
| `POST /v1/sessions/{id}/append` | `session.append` | [[017-external-runners-handoff-fork]]'s |
| `POST /v1/sessions/{id}/handoff` | `session.handoff` | [[017-external-runners-handoff-fork]]'s |
| `PUT /v1/sessions/{id}/blobs/{digest}` | `session.append` | [[017-external-runners-handoff-fork]]'s |
| `GET /v1/sessions/{id}/inbox` | `session.append` | [[017-external-runners-handoff-fork]]'s |
| `PUT /v1/triggers/{name}`, `GET /v1/triggers`, `GET /v1/triggers/{ref}`, `DELETE /v1/triggers/{ref}` | `trigger.*` | apply, list, get, delete a Trigger ([[022-triggers]]) |
| `POST /v1/triggers/{ref}/fire` | `trigger.fire` | deliver one event to a trigger, or fire a schedule now; answers the firing ([[022-triggers]]) |
| `GET /v1/triggers/{ref}/firings` | `trigger.read` | a trigger's firings, newest first ([[022-triggers]]) |
| `POST /v1/credentials` | `credential.create` | create a write-only Credential; the value is never answered ([[018-credentials-and-secrets]]) |
| `GET /v1/credentials`, `GET /v1/credentials/{ref}`, `DELETE /v1/credentials/{ref}` | `credential.list`, `credential.read`, `credential.delete` | metadata only |
| `PUT /v1/memory-stores/{name}`, `GET /v1/memory-stores`, `GET /v1/memory-stores/{ref}`, `DELETE /v1/memory-stores/{ref}` | `memory_store.*` | apply, list, get, delete a MemoryStore ([[020-memory-stores]]) |
| `GET /v1/memory-stores/{ref}/documents`, `GET`, `PUT` and `DELETE /v1/memory-stores/{ref}/documents/{path}`, `GET /v1/memory-stores/{ref}/documents/{path}/versions` | `memory_store.read`, `memory_store.write` | documents and their versions; semantics [[020-memory-stores]] |

### Agent names

An agent's name is unique within its owner, not across the
installation: two owners may each hold an agent named `coding-agent`,
and each reaches their own by it. The owner is the context of the apply
that creates the agent: the organization the caller's token names in
its `org_id` claim, or the caller as a person when it names none
([[036-organization-owners]]). Every name the API reads is read among
the agents of the caller's context: the `{name}` of an apply, a `{ref}`
that is not an `agent_` id, a session create's `agent`, the `agent`
filter of a session list, and a manifest's references ([[003-manifest]]).
An apply of a name the context does not hold creates the context's
agent, whoever else holds one of the name. A list of agents holds the
context's, and a list of sessions the sessions of the context's agents. A name only another subject holds
answers `not_found`, or `unknown_reference` in a manifest, the same
bytes as a name nobody holds, so a name tells no one whether another
subject's agent exists. An `agent_` id names its agent whoever owns it,
and the authorizer decides the action as for any other object; an
administrator reaches another subject's agent by its id.

`metadata.name` is the identifier every route and reference names.
`metadata.displayName` is the optional name a person reads, one line
of at most 200 characters ([[003-manifest]]); every answer that carries
an agent, the apply, a read by name or id, a version, and each item of
the list, carries it as last applied, and an agent applied without one
carries none, so a client shows `metadata.name` in its place.

### Creating a session

| Field | Required | Meaning |
|---|---|---|
| `agent` | yes | an agent reference: an `agent_` id, or a name among the caller's own agents (above), each optionally `@<n>`; the session pins its latest version or the one named |
| `runner` | no, default `hosted` | `hosted` or `external` ([[017-external-runners-handoff-fork]]) |
| `id` | no | an `external` session's id chosen by its local runner; otherwise the server mints one |
| `message` | no | the text of the first `user.message` |
| `machine`, `resources`, `budget`, `limits`, `capture`, `end_on_idle`, `title`, `metadata` | no | the Session fields of [[004-session-log]], each capped by the agent's and the authorizer's |

The initiator is the verified subject. A create that the authorizer
allows with `limits` applies them ([[006-identity]]): the budget, the
turn timeout and the age are the lowest of the request's, the agent's
and the authorizer's; `retention` and `scope` are the authorizer's. A
hosted session runs on a Cella machine, or on the server's own host
when the operator set `TOPOS_HOST_SESSIONS=on` ([[009-machines]]);
otherwise an agent whose `machine.kind` is `host` answers
`machine_unavailable`. An agent whose `spec.machine` asks for nothing
beyond the default, `kind: host` alone or no machine at all, which its
resolved spec cannot tell apart ([[003-manifest]]), runs on a Cella
sandbox of the default image on a server with `TOPOS_CELLA_URL` set and
host sessions off, since the manifest's host default is a local run's;
with host sessions on, or without Cella, it keeps `host`. The session
records the machine it runs on, and `session.create` names that kind as
`machine`. One function on the server decides it, and every runner
drives the machine the session records. The agent's model must be one
the installation runs ([[007-models]]): a model no source gives an input
window and an output limit is `model_unknown`, and one whose figures
could not be read `model_unavailable`, before anything is asked or
stored. `runner: external`, `id` and
`machine` are refused with `invalid_request` until
[[017-external-runners-handoff-fork]] and [[009-machines]] take them.
`resources` names repositories alone, at most 8, each
`{"type":"repository","url","ref"}` with an `https` URL that names its
host and holds no credential and a `ref` that is a branch, a tag or a
commit ([[019-git]]); anything else is `invalid_request`, a memory store
included, which is its agent's ([[020-memory-stores]]). A create that
names no repositories, `resources` absent or an empty list, records the
`spec.repositories` of the agent version it pins ([[003-manifest]]); one
that names any records those alone. A session of an archived agent is
`conflict`.

### Changing the model and its effort

`PATCH /v1/sessions/{id}` changes a field of the session. It takes the
model alone for now, its name, its reasoning effort or both, and any
other member is `invalid_request`:

```json
{"model": {"name": "anthropic/claude-sonnet-4-5"}}
{"model": {"effort": "high"}}
{"model": {"name": "openai/gpt-5", "effort": "low"}}
```

A member left out keeps what the session runs: a body without `name`
keeps the model, and one without `effort` keeps the effort. `effort` is
one of `minimal`, `low`, `medium` and `high`, the values of an agent's
`spec.model.effort` ([[003-manifest]]), or `""`, which returns to the
agent's own effort; any other value is `invalid_request`, and so is a
`model` that names neither member. The effort holds across a change of
the model, and a model that takes no reasoning effort ignores it
([[007-models]]).

The name is resolved as an agent's model is ([[007-models]]): the
agent's own model's name is the agent's `spec.model` as it names it,
its base URL, credential and figures included, and any other name is
that model alone through the installation's model connection, with the
embedded catalog's figures and those the Lux door's model list serves
for it, and none of the agent's. The installation runs the model by the
one check a session's create makes of its agent's model ([[007-models]]),
so a switch takes every model a session could have been created with,
one only a Lux door serves included; a model the check refuses is
`model_unknown`, or `model_unavailable` when its figures could not be
read, and changes nothing. A body without `name` resolves nothing.

The route asks `session.read` first, so a caller who may not read the
session hears `not_found` whatever the body names. A session that ended
is `conflict`. The name is resolved next, and only then is
`session.update` asked, with `session_id` and what the body changes in
the resource beside the session's `agent`, `owner` and `runner`
([[006-identity]]): `model`, the name, when the body names one, and
`effort`, the effort the next turn runs at, the agent's own for `""`,
which is itself `""` for an agent that names none, when the body names
one. An effort change alone carries no `model`. The authorizer decides
whether the session may use that model, and may widen the session's
model key to it, knowing that the model exists; an effort change alone
reaches no new model, so it needs no wider key. A deny is `forbidden`,
with the authorizer's reason in `details.reason` (such as
`model_not_offered`), and the session keeps its model and its effort.
An allowed change appends one event, and the answer is the Session with
its `model`:

```json
{"type": "session.model_changed", "payload": {"by": {"subject": "https://login.example|alice", "kind": "person"},
  "old": {"name": "anthropic/claude-haiku-4-5"}, "new": {"name": "anthropic/claude-sonnet-4-5", "effort": "high"}}}
```

`old` is the model and the effort the session ran before, the agent's
until a first change, and `new` the ones its next turn runs; `effort` is
absent from either for the model's own default, when the agent names
none. A change to the model and the effort the session already runs
appends nothing. The Session's `model` is the latest `new`, and absent
until a first change, when the session runs its agent's model and effort
([[004-session-log]]). A turn runs on the model and the effort its
session names when it starts: a change while a turn runs changes nothing
of that turn, and the next turn, in the same drive or a later one, runs
on the new model with its own window, output limit and prices, and at
the new effort ([[007-models]]). An authorizer that scopes a session's
model keys to its models widens them to the new model before it allows
the switch, so the keys the runner holds reach it
([[018-credentials-and-secrets]]). A thread keeps the model of the agent
it names, and its effort when that agent names one; a thread whose agent
names no effort runs at the session's, as it runs at its parent agent's
until a change ([[013-threads-and-subagents]]).

### Archiving a session

`POST /v1/sessions/{id}/archive` sets the session's `archived_at`
([[004-session-log]]) and `POST /v1/sessions/{id}/unarchive` clears it;
both take an empty body and answer the Session. Archiving files a
session away from the lists and changes nothing else: the session, its
log and its blobs stay, it is read by id, streamed and forked as
before, and its retention runs as before ([[014-store]]). It appends no
event, since an ended session's log takes no more.

Only an ended session is archived: an idle or running one is
`conflict`, and is ended first with `POST /v1/sessions/{id}/end`, so
archiving never stops work and an unarchive restores exactly what was
there. Archiving an archived session, or unarchiving one that is not,
changes nothing and answers the Session. Both routes ask `session.read`
first, so a caller who may not read the session hears `not_found`, and
then `session.update` with `session_id` and `archived`, `true` or
`false`, beside the session's `agent`, `owner` and `runner`
([[006-identity]]); a deny is `forbidden` and changes nothing.

`GET /v1/sessions` leaves archived sessions out. `?archived=true` lists
only archived ones, `?archived=any` lists both, and `?archived=false`
is the default; any other value is `invalid_request`.

### Summarizing sessions

`GET /v1/sessions/summary` answers how many sessions `GET /v1/sessions`
would list for the caller, and how many agents they belong to, in one
read, so a client that shows an overview counts every session without
paging through them:

```json
{"sessions": {"running": 2, "waiting_for_approval": 1, "idle": 3, "ended": 10}, "agents": 3}
```

The four counts are disjoint and together are every session the list
would page through: `running` and `ended` are the sessions of that
status, `waiting_for_approval` the idle ones whose stop reason is
`tool_confirmation`, where a call or a step-up approval waits for a
person ([[012-permissions-and-approvals]]), and `idle` every other idle
session. `agents` is the number of distinct agents among those
sessions. A session of a status this version does not know is in no
count.

The summary is scoped exactly as the list. It asks `session.list` with
the list's fields, an empty `status` and the `runner` filter, applies
the owners the decision narrows the list to ([[006-identity]]), and
takes the list's `agent`, `runner` and `archived` filters with their
defaults and their refusals, so archived sessions are left out unless
`archived` asks for them. It takes no `status`, `limit` or `cursor`. A
count reveals nothing the list would not, so it has no action of its
own. An `agent` name the caller holds no agent of answers every count
zero, as the list answers an empty page.

A store counts without reading the sessions' bodies where it can: the
Postgres store counts in one query over the columns the list filters
on, and the directory and memory stores count the headers they read for
a list ([[014-store]]). A store that offers no count is summarized by
paging through its list.

### Sending events

`POST /v1/sessions/{id}/events` takes one event whose `type` is
`user.message`, `user.interrupt`, `user.tool_confirmation` or
`user.tool_result`, with its payload. The server sets `sender` from the
verified subject and ignores one in the body, assigns the `id` and the
`time`, and appends it; the answer is the appended event with its
`seq`. When the session's writer is external, the event goes to the
session's inbox instead of the log ([[017-external-runners-handoff-fork]]),
and the answer carries no `seq`. Any other type is `invalid_request`.
A send to an `ended` session is `conflict`, and so is a
`user.tool_confirmation` or a `user.tool_result` that answers no call
waiting for it: a call never asked, answered already, or waiting for
the other kind of answer.

### Images and files on a message

A `user.message`'s payload holds `content`, text blocks and inline
images, and `attachments`, the files it carries; at least one of the
two is set:

```json
{"type": "user.message", "payload": {
  "content": [{"type": "text", "text": "Why does March dip in this chart and in the data?"},
              {"type": "image", "image": {"media_type": "image/png", "data": "iVBORw0KGgo..."}}],
  "attachments": [{"name": "sales.csv", "media_type": "text/csv", "data": "bW9udGgsdG90YWwK..."}]}}
```

| Limit | Constant | Value |
|---|---|---|
| images in one message | `MaxImages` | 8 |
| one image, decoded | `MaxImageBytes` | 5 MiB, the read tool's image limit ([[008-tools]]) |
| files in one message | `MaxAttachments` | 8 |
| one file, decoded | `MaxAttachmentBytes` | 5 MiB |
| a file's name | `MaxAttachmentName` | 255 bytes |

An image is base64 `data` of PNG, JPEG, GIF or WebP whose bytes are
the format its `media_type` names; an image by URL is refused, since
its size cannot be held to the limit, and so is a block of any type
but `text` and `image`. A file is base64 `data` with a `name` that is
one path segment, neither `.` nor `..`, without a path separator, a
control or a bidirectional character, no other file of the message
named the same, and an optional `media_type`, which the file's bytes
give when it is absent. An image or a file past
its limit is `attachment_too_large` (413) and names which; every other
refusal is `invalid_request`; the event body, at most 8 MiB, bounds a
message's images and files together in their base64 form, and past it
the answer is `payload_too_large`. Nothing of a refused message is
stored.

The server stores each file as a blob of the session before the event
that names it ([[014-store]]), and the appended event records the file
without its data, at `attachments/<event id>/<name>` relative to the
working directory: each message's files go in a directory named after
its `user.message`'s id, which the server mints before it stores them,
so two messages that each carry a `sales.csv` write two paths and
neither file replaces the other.

```json
{"attachments": [{"name": "sales.csv", "media_type": "text/csv", "size": 1204,
  "blob": "sha256:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08", "path": "attachments/evt_01J9Z3Q4W8KX6T0M2V5N7R1B3C/sales.csv"}]}
```

The model reads the paths after the message's content ([[004-session-log]]):

```
Attached files, in the working directory:
- attachments/evt_01J9Z3Q4W8KX6T0M2V5N7R1B3C/sales.csv (text/csv, 1204 bytes)
```

The runner writes each file at its path when the session's machine
opens, before the tool call that opened it runs, and, while the machine
is open, before the next step's request, so a model that reads a path
finds the file; a machine opened on demand is not opened for it
([[016-runners]]). Each write is recorded as `attachments.delivered`
with the paths written, once per machine: a later machine the session
moves to is given every file again. A file that cannot be written is a
`session.error` `attachment_unavailable`, retryable, and is tried again
at the next turn; the turn runs on. When the working directory is a
repository, `/attachments/` is added to its `.git/info/exclude`, so the
session's commits take a file only when the agent adds it by force.

An image reaches the model as an image block when the model's figures
say it takes images ([[007-models]]); for any other model each image of
a message is replaced in the request by a note that the model cannot
see it, and the turn runs. Whether a model takes images is the
embedded catalog's, from OpenRouter's model list ([[007-models]]), on a
Lux door or a provider's own API alike: Claude from 4.5, GPT from 4o
and Gemini from 2.5 take them, each model OpenRouter lists.

`POST /v1/sessions/{id}/events/{event_id}/redact` redacts only an event
that carries content a person, the model or a tool put in the log
(`user.message`, `user.tool_result`, `agent.message`, `agent.tool_use`,
`tool.result`, `context.compacted`); any other event is part of the
session's record, its verdicts, confirmations, model requests and
statuses, and a redaction of it is `invalid_request`, so no redaction
rewrites the audit or resets the budget.

### The stream

`GET /v1/sessions/{id}/stream?from_seq=<n>` answers
`text/event-stream`: every event from `n` (default 1), then each new
one as it is appended, from any replica. Each frame is `id: <seq>`,
`event: <type>`, and `data:` the event's JSON. A reconnect with
`Last-Event-ID` resumes after that sequence. A comment line is sent
every 15 seconds. The stream closes after the event that ends the
session. A subject holds at most 16 streams open at once on one
replica; the next is `rate_limited`, without `Retry-After`, until one
of them ends.

With `?deltas=1` the stream also carries the session's live output as a
response arrives ([[005-harness-loop]]), from whichever replica's runner
drives the session ([[016-runners]]): frames of `event: delta` and
`data:` one delta, with no `id`. A frame without an `id` leaves a
browser's last event id as it was, so a reconnect resumes the log where
it was. `deltas=0` or no parameter carries the log's events alone. A
delta is one of two shapes:

```
{"thread":"evt_...","turn":3,"step":1,"block":0,"kind":"text","text":"Hel"}
{"thread":"evt_...","turn":3,"step":1,"reset":true}
```

| Field | Meaning |
|---|---|
| `thread` | the thread whose response it is; absent for the session's own thread, as on events |
| `turn`, `step` | the turn and the step of the response, as the step's events carry them |
| `block` | the index of the response's content block the text belongs to |
| `kind` | `text`, `thinking`, or `tool_input`: a tool call's arguments as the model writes them |
| `text` | the next run of the block's text, to append to what the step's earlier deltas carried for that block; at most 1024 bytes |
| `reset` | the step's request is sent again: discard what its deltas carried |

Deltas are best effort. They are never appended and never replayed, a
replay from any sequence holds none, and a delta that cannot be
delivered is dropped rather than slowing the turn. The step's
`agent.message` is the record, so a client that misses deltas loses
nothing: it shows the deltas of a step until the step's `agent.message`
arrives and then shows the message. The last deltas of a step and its
`agent.message` travel apart, so a client ignores a delta of a step
whose `agent.message` it already holds. A stream that joins a step
midway receives the step's deltas from there on.

### Paging, idempotency, limits

A list takes `limit` (default 50, at most 500) and `cursor`, and
answers `{"items":[...],"next_cursor":"..."}`, `next_cursor` absent on
the last page, with the next page's URL also in a `Link` header with
`rel="next"`; a cursor is opaque. A session's answers carry its stream's
URL in a `Link` header with `rel="stream"` ([[030-shared-origin]]). Every `POST` takes an optional
`Idempotency-Key` header: a repeat from the same subject with the same
key and the same body within 24 hours answers the stored answer; the
same key with a different body is `idempotency_conflict`. A manifest or
JSON body is at most 1 MiB and an event body at most 8 MiB.

### Errors

Every error is `{"error":{"code","message","details"}}` through
`latere.ai/x/pkg/httpjson`: one code, one fixed sentence for a person in
`message`, and the developer detail in `details` (`details.detail`, and
`details.problems` for a manifest, each `{document, path, detail}`). A
`not_found` carries no details, so a denied read and an absent object
answer the same bytes; a path's id that is not in its object's form
(`ses_` and a ULID for a session) names no object and answers
`not_found` too. An error of no code in the table is `internal`,
500, and its cause stays in the server's log.

A `forbidden` keeps its one sentence and carries the authorizer's
reason for the deny in `details.reason`, so a client can say why and
what to do next without the sentence changing:

```json
{"error": {"code": "forbidden", "message": "You may not do this.",
  "details": {"detail": "the authorizer denied session.create", "reason": "agents_not_enabled"}}}
```

The reason is the authorizer's own snake_case token ([[006-identity]]);
a deny without one, or with text of another shape, carries none. The
guard answers `forbidden` only where the refusal discloses nothing the
caller may not see. A session create's reason may be about the agent
it names: whose it is, the organization it belongs to, its budget. It
is passed when the agent is the caller's own, the one the caller
applied, and for another subject's agent only when the caller may read
it (the guard asks `agent.read`).
The authz wire carries a reason and nothing beside it, so a detail such
as which permission exceeded the initiator's reach is not passed until
the wire carries one.

### The OpenAPI document

`api/openapi.yaml` is committed and embedded, served at
`GET /v1/openapi.yaml`, and generated from the route table and the
error table by `go generate ./internal/server`; the generated file
differing from the committed one fails the gate.

An operation's `summary` is the name of its action, the label a
reference lists the operation by: at most four words, verb first,
without a closing period, and no two operations share one. What the
operation does, and what its body and its answer hold, is its
`description`, which every operation has.

## Not in this spec

The Session and Event schema ([[004-session-log]]); the manifest kinds
([[003-manifest]]); the actions and verification ([[006-identity]]);
fork, append, handoff and the inbox
([[017-external-runners-handoff-fork]]); the runner routes on the
internal listener ([[016-runners]]); base paths ([[030-shared-origin]]).
